prompt you, or be blocked.</p>\n71: <p>As of <code>v1.1.1</code>, the legacy <code>tools</code> boolean config is deprecated and has been merged into <code>permission</code>. The old <code>tools</code> config is still supported for backwards compatibility.</p>\n72: <hr />\n73: <h2 id=\"actions\">Actions</h2>\n74: <p>Each permission rule resolves to one of:</p>\n75: <ul>\n76: <li><code>\"allow\"</code> — run without approval</li>\n77: <li><code>\"ask\"</code> — prompt for approval</li>\n78: <li><code>\"deny\"</code> — block the action</li>\n79: </ul>\n80: <hr />\n81: <h2 id=\"auto-mode\">Auto mode</h2>\n82: <p>Start OpenCode with <code>--auto</code> to automatically approve permission requests that are not explicitly denied.</p>\n83: <pre><code class=\"language-bash\">opencode --auto\n84: </code></pre>\n85: <p>You can also use auto mode with <a href=\"cli.html#run\"><code>opencode run</code></a>.</p>\n86: <pre><code class=\"language-bash\">opencode run --auto &quot;Refactor this module&quot;\n87: </code></pre>\n88: <p>Explicit <code>\"deny\"</code> rules are still enforced. Auto mode only changes requests that would otherwise ask for approval.</p>\n89: <p>In the TUI, open the command palette and select <strong>Enable auto-approve permissions</strong> or <strong>Disable auto-approve permissions</strong> to change modes. When auto mode is active, the prompt displays a muted <code>auto</code> indicator next to the current agent.</p>\n90: <hr />\n91: <h2 id=\"configuration\">Configuration</h2>\n92: <p>You can set permissions globally (with <code>*</code>), and override specific tools.</p>\n93: <pre><code class=\"language-json\">{\n94:   &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n95:   &quot;permission&quot;: {\n96:     &quot;*&quot;: &quot;ask&quot;,\n97:     &quot;bash&quot;: &quot;allow&quot;,\n98:     &quot;edit&quot;: &quot;deny&quot;\n99:   }\n100: }\n101: </code></pre>\n102: <p>You can also set all permissions at once:</p>\n103: <pre><code class=\"language-json\">{\n104:   &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n105:   &quot;permission&quot;: &quot;allow&quot;\n106: }\n107: </code></pre>\n108: <hr />\n109: <h2 id=\"granular-rules-object-syntax\">Granular Rules (Object Syntax)</h2>\n110: <p>For most permissions, you can use an object to apply different actions based on the tool input.</p>\n111: <pre><code class=\"language-json\">{\n112:   &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n113:   &quot;permission&quot;: {\n114:     &quot;bash&quot;: {\n115:       &quot;*&quot;: &quot;ask&quot;,\n116:       &quot;git *&quot;: &quot;allow&quot;,\n117:       &quot;npm *&quot;: &quot;allow&quot;,\n118:       &quot;rm *&quot;: &quot;deny&quot;,\n119:       &quot;grep *&quot;: &quot;allow&quot;\n120:     },\n121:     &quot;edit&quot;: {\n122:       &quot;*&quot;: &quot;deny&quot;,\n123:       &quot;packages/web/src/content/docs/*.mdx&quot;: &quot;allow&quot;\n124:     }\n125:   }\n126: }\n127: </code></pre>\n128: <p>Rules are evaluated by pattern match, with the <strong>last matching rule winning</strong>. A common pattern is to put the catch-all <code>\"*\"</code> rule first, and more specific rules after it.</p>\n129: <h3 id=\"wildcards\">Wildcards</h3>\n130: <p>Permission patterns use simple wildcard matching:</p>\n131: <ul>\n132: <li><code>*</code> matches zero or more of any character</li>\n133: <li><code>?</code> matches exactly one character</li>\n134: <li>All other characters match literally</li>\n135: </ul>\n136: <h3 id=\"home-directory-expansion\">Home Directory Expansion</h3>\n137: <p>You can use <code>~</code> or <code>$HOME</code> at the start of a pattern to reference your home directory. This is particularly useful for <a href=\"#external-directories\"><code>external_directory</code></a> rules.</p>\n138: <ul>\n139: <li><code>~/projects/*</code> -&gt; <code>/Users/username/projects/*</code></li>\n140: <li><code>$HOME/projects/*</code> -&gt; <code>/Users/username/projects/*</code></li>\n141: <li><code>~</code> -&gt; <code>/Users/username</code></li>\n142: </ul>\n143: <h3 id=\"external-directories\">External Directories</h3>\n144: <p>Use <code>external_directory</code> to allow tool calls that touch paths outside the working directory where OpenCode was started. This applies to any tool that takes a path as input (for example <code>read</code>, <code>edit</code>, <code>glob</code>, <code>grep</code>, and many <code>bash</code> commands).</p>\n145: <p>Home expansion (like <code>~/...</code>) only affects how a pattern is written. It does not make an external path part of the current workspace, so paths outside the working directory must still be allowed via <code>external_directory</code>.</p>\n146: <p>For example, this allows access to everything under <code>~/projects/personal/</code>:</p>\n147: <pre><code class=\"language-json\">{\n148:   &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n149:   &quot;permission&quot;: {\n150:     &quot;external_directory&quot;: {\n151:       &quot;~/projects/personal/**&quot;: &quot;allow&quot;\n152:     }\n153:   }\n154: }\n155: </code></pre>\n156: <p>Any directory allowed here inherits the same defaults as the current workspace. Since <a href=\"#defaults\"><code>read</code> defaults to <code>allow</code></a>, reads are also allowed for entries under <code>external_directory</code> unless overridden. Add explicit rules when a tool should be restricted in these paths, such as blocking edits while keeping reads:</p>\n157: <pre><code class=\"language-json\">{\n158:   &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n159:   &quot;permission&quot;: {\n160:     &quot;external_directory&quot;: {\n161:       &quot;~/projects/personal/**&quot;: &quot;allow&quot;\n162:     },\n163:     &quot;edit&quot;: {\n164:       &quot;~/projects/personal/**&quot;: &quot;deny&quot;\n165:     }\n166:   }\n167: }\n168: </code></pre>\n169: <p>Keep the list focused on trusted paths, and layer extra allow or deny rules as needed for other tools (for example <code>bash</code>).</p>\n170: <hr />\n171: <h2 id=\"available-permissions\">Available Permissions</h2>\n172: <p>OpenCode permissions are keyed by tool name, plus a couple of safety guards:</p>\n173: <ul>\n174: <li><code>read</code> — reading a file (matches the file path)</li>\n175: <li><code>edit</code> — all file modifications (covers <code>edit</code>, <code>write</code>, <code>patch</code>)</li>\n176: <li><code>glob</code> — file globbing (matches the glob pattern)</li>\n177: <li><code>grep</code> — content search (matches the regex pattern)</li>\n178: <li><code>bash</code> — running shell commands (matches parsed commands like <code>git status --porcelain</code>)</li>\n179: <li><code>task</code> — launching subagents (matches the subagent type)</li>\n180: <li><code>skill</code> — loading a skill (matches the skill name)</li>\n181: <li><code>lsp</code> — running LSP queries (currently non-granular)</li>\n182: <li><code>question</code> — asking the user questions during execution</li>\n183: <li><code>webfetch</code> — fetching a URL (matches the URL)</li>\n184: <li><code>websearch</code> — web search (matches the query)</li>\n185: <li><code>external_directory</code> — triggered when a tool touches paths outside the project working directory</li>\n186: <li><code>doom_loop</code> — triggered when the same tool call repeats 3 times with identical input</li>\n187: </ul>\n188: <hr />\n189: <h2 id=\"defaults\">Defaults</h2>\n190: <p>If you don’t specify anything, OpenCode starts from permissive defaults:</p>\n191: <ul>\n192: <li>Most permissions default to <code>\"allow\"</code>.</li>\n193: <li><code>doom_loop</code> and <code>external_directory</code> default to <code>\"ask\"</code>.</li>\n194: <li><code>read</code> is <code>\"allow\"</code>, but <code>.env</code> files are denied by default:</li>\n195: </ul>\n196: <pre><code class=\"language-json\">{\n197:   &quot;permission&quot;: {\n198:     &quot;read&quot;: {\n199:       &quot;*&quot;: &quot;allow&quot;,\n200:       &quot;*.env&quot;: <li><code>always</code> — approve future requests matching the suggested patterns (for the rest of the current OpenCode session)</li>\n213: <li><code>reject</code> — deny the request</li>\n214: The old <code>tools</code> config is still supported for backwards compatibility.</p>\n<hr />\n<h2 id=\"actions\">Actions</h2>\n<p>Each permission rule resolves to one of:</p>\n<ul>\n<li><code>\"allow\"</code> — run without approval</li>\n<li><code>\"ask\"</code> — prompt for approval</li>\n<li><code>\"deny\"</code> — block the action</li>\n</ul>\n<hr />\n<h2 id=\"auto-mode\">Auto mode</h2>\n<p>Start OpenCode with <code>--auto</code> to automatically approve permission requests that are not explicitly denied.</p>\n<pre><code class=\"language-bash\">opencode --auto\n</code></pre>\n<p>You can also use auto mode with <a href=\"cli.html#run\"><code>opencode run</code></a>.</p>\n<pre><code class=\"language-bash\">opencode run --auto &quot;Refactor this module&quot;\n</code></pre>\n<p>Explicit <code>\"deny\"</code> rules are still enforced. Auto mode only changes requests that would otherwise ask for approval.</p>\n<p>In the TUI, open the command palette and select <strong>Enable auto-approve permissions</strong> or <strong>Disable auto-approve permissions</strong> to change modes. When auto mode is active, the prompt displays a muted <code>auto</code> indicator next to the current agent.</p>\n<hr />\n<h2 id=\"configuration\">Configuration</h2>\n<p>You can set permissions globally (with <code>*</code>), and override specific tools.</p>\n<pre><code class=\"language-json\">{\n  &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n  &quot;permission&quot;: {\n    &quot;*&quot;: &quot;ask&quot;,\n    &quot;bash&quot;: &quot;allow&quot;,\n    &quot;edit&quot;: &quot;deny&quot;\n  }\n}\n</code></pre>\n<p>You can also set all permissions at once:</p>\n<pre><code class=\"language-json\">{\n  &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n  &quot;permission&quot;: &quot;allow&quot;\n}\n</code></pre>\n<hr />\n<h2 id=\"granular-rules-object-syntax\">Granular Rules (Object Syntax)</h2>\n<p>For most permissions, you can use an object to apply different actions based on the tool input.</p>\n<pre><code class=\"language-json\">{\n  &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n  &quot;permission&quot;: {\n    &quot;bash&quot;: {\n      &quot;*&quot;: &quot;ask&quot;,\n      &quot;git *&quot;: &quot;allow&quot;,\n      &quot;npm *&quot;: &quot;allow&quot;,\n      &quot;rm *&quot;: &quot;deny&quot;,\n      &quot;grep *&quot;: &quot;allow&quot;\n    },\n    &quot;edit&quot;: {\n      &quot;*&quot;: &quot;deny&quot;,\n      &quot;packages/web/src/content/docs/*.mdx&quot;: &quot;allow&quot;\n    }\n  }\n}\n</code></pre>\n<p>Rules are evaluated by pattern match, with the <strong>last matching rule winning</strong>. loading a skill (matches the skill name)</li>\n<li><code>lsp</code> — running LSP queries (currently non-granular)</li>\n<li><code>question</code> — asking the user questions during Singular names (e.g., <code>agent/</code>) are also supported for backwards compatibility.</p>\n</div>\n<hr />\n<h3 id=\"remote\">Remote</h3>\n<p>Organizations can provide default configuration via the <code>.well-known/opencode</code> endpoint. This is fetched automatically when you authenticate with a provider that supports it.</p>\n<p>Remote config is loaded first, serving as the base layer. All other config sources (global, project) can override these defaults.</p>\n<p>For example, if your organization provides MCP servers that are disabled by default:</p>\n<pre><code class=\"language-json\">{\n  &quot;mcp&quot;: {\n    &quot;jira&quot;: {\n      &quot;type&quot;: &quot;remote&quot;,\n      &quot;url&quot;: &quot;https://jira.example.com/mcp&quot;,\n      &quot;enabled&quot;: false\n    }\n  }\n}\n</code></pre>\n<p>You can enable specific servers in your local config:</p>\n<pre><code class=\"language-json\">{\n  &quot;mcp&quot;: {\n    &quot;jira&quot;: {\n      &quot;type&quot;: &quot;remote&quot;,\n      &quot;url&quot;: &quot;https://jira.example.com/mcp&quot;,\n      &quot;enabled&quot;: true\n    }\n  }\n}\n</code></pre>\n<hr />\n<h3 id=\"global\">Global</h3>\n<p>Place your global OpenCode config in <code>~/.config/opencode/opencode.json</code>. Use global config for user-wide server/runtime preferences like providers, models, and permissions.</p>\n<p>For TUI-specific settings, use <code>~/.config/opencode/tui.json</code>.</p>\n<p>Global config overrides remote organizational defaults.</p>\n<hr />\n<h3 id=\"per-project\">Per project</h3>\n<p>Add <code>opencode.json</code> in your project root. Project config has the highest precedence among standard config files - it overrides both global and remote configs.</p>\n<p>For project-specific TUI settings, add <code>tui.json</code> alongside it.</p>\n<div class=\"aside\">\n<div class=\"aside-t\">Tip</div>\n<p>Place project specific config in the root of your project.</p>\n</div>\n<p>When OpenCode starts up, it first looks for a config file in the current directory, then traverses up to the nearest Git directory.</p>\n<p>This is also safe to be checked into Git and uses the same schema as the global one.</p>\n<hr />\n<h3 id=\"custom-path\">Custom path</h3>\n<p>Specify a custom config file path using the <code>OPENCODE_CONFIG</code> environment variable.</p>\n<pre><code class=\"language-bash\">export OPENCODE_CONFIG=/path/to/my/custom-config.json\nopencode run &quot;Hello world&quot;\n</code></pre>\n<p>Custom config is loaded between global and project configs in the precedence order.</p>\n<hr />\n<h3 id=\"custom-directory\">Custom directory</h3>\n<p>Specify a custom config directory using the <code>OPENCODE_CONFIG_DIR</code>\nenvironment variable.
