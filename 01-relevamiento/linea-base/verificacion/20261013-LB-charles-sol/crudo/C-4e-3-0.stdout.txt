href=\"windows-wsl.html\">Windows (WSL)</a>\n<a href=\"zen.html\">Zen</a></nav>\n<main><h1>Config</h1>\n<p>You can configure OpenCode using a JSON config file.</p>\n<hr />\n<h2 id=\"format\">Format</h2>\n<p>OpenCode supports both <strong>JSON</strong> and <strong>JSONC</strong> (JSON with Comments) formats.</p>\n<pre><code class=\"language-jsonc\">{\n  &quot;$schema&quot;: &quot;https://opencode.ai/config.json&quot;,\n  &quot;model&quot;: &quot;anthropic/claude-sonnet-4-5&quot;,\n  &quot;autoupdate&quot;: true,\n  &quot;server&quot;: {\n    &quot;port&quot;: 4096,\n  },\n}\n</code></pre>\n<hr />\n<h2 id=\"locations\">Locations</h2>\n<p>You can place your config in a couple of different locations and they have a\ndifferent order of precedence.</p>\n<div class=\"aside\">\n<div class=\"aside-t\">Note</div>\n<p>Configuration files are <strong>merged together</strong>, not replaced.</p>\n</div>\n<p>Configuration files are merged together, not replaced. Settings from the following config locations are combined. Later configs override earlier ones only for conflicting keys. Non-conflicting settings from all configs are preserved.</p>\n<p>For example, if your global config sets <code>autoupdate: true</code> and your project config sets <code>model: \"anthropic/claude-sonnet-4-5\"</code>, the final configuration will include both settings.</p>\n<hr />\n<h3 id=\"precedence-order\">Precedence order</h3>\n<p>Config sources are loaded in this order (later sources override earlier ones):</p>\n<ol>\n<li><strong>Remote config</strong> (from <code>.well-known/opencode</code>) - organizational defaults</li>\n<li><strong>Global config</strong> (<code>~/.config/opencode/opencode.json</code>) - user preferences</li>\n<li><strong>Custom config</strong> (<code>OPENCODE_CONFIG</code> env var) - custom overrides</li>\n<li><strong>Project config</strong> (<code>opencode.json</code> in project) - project-specific settings</li>\n<li><strong><code>.opencode</code> directories</strong> - agents, commands, plugins</li>\n<li><strong>Inline config</strong> (<code>OPENCODE_CONFIG_CONTENT</code> env var) - runtime overrides</li>\n<li><strong>Managed config files</strong> (<code>/Library/Application Support/opencode/</code> on macOS) - admin-controlled</li>\n<li><strong>macOS managed preferences</strong> (<code>.mobileconfig</code> via MDM) - highest priority, not user-overridable</li>\n</ol>\n<p>This means project configs can override global defaults, and global configs can override remote organizational defaults. Managed settings override everything.</p>\n<div class=\"aside\">\n<div class=\"aside-t\">Note</div>\n<p>The <code>.opencode</code> and <code>~/.config/opencode</code> directories use <strong>plural names</strong> for subdirectories: <code>agents/</code>, <code>commands/</code>, <code>modes/</code>, <code>plugins/</code>, <code>skills/</code>, <code>tools/</code>, and <code>themes/</code>. Singular names (e.g., <code>agent/</code>) are also supported for backwards compatibility.</p>\n</div>\n<hr />\n<h3 id=\"remote\">Remote</h3>\n<p>Organizations can provide default configuration via the <code>.well-known/opencode</code> endpoint. This is fetched automatically when you authenticate with a provider that supports it.</p>\n<p>Remote config is loaded first, serving as the base layer. All other config sources (global, project) can override these defaults.</p>\n<p>For example, if your organization provides MCP servers that are disabled by default:</p>\n<pre><code class=\"language-json\">{\n  &quot;mcp&quot;: {\n    &quot;jira&quot;: {\n      &quot;type&quot;: &quot;remote&quot;,\n      &quot;url&quot;: &quot;https://jira.example.com/mcp&quot;,\n      &quot;enabled&quot;: false\n    }\n  }\n}\n</code></pre>\n<p>You can enable specific servers in your local config:</p>\n<pre><code class=\"language-json\">{\n  &quot;mcp&quot;: {\n    &quot;jira&quot;: {\n      &quot;type&quot;: &quot;remote&quot;,\n      &quot;url&quot;: &quot;https://jira.example.com/mcp&quot;,\n      &quot;enabled&quot;: true\n    }\n  }\n}\n</code></pre>\n<hr />\n<h3 id=\"global\">Global</h3>\n<p>Place your global OpenCode config in <code>~/.config/opencode/opencode.json</code>. Use global config for user-wide server/runtime preferences like providers, models, and permissions.</p>\n<p>For TUI-specific settings, use <code>~/.config/opencode/tui.json</code>.</p>\n<p>Global config overrides remote organizational defaults.</p>\n<hr />\n<h3 id=\"per-project\">Per project</h3>\n<p>Add <code>opencode.json</code> in your project root. Project config has the highest precedence among standard config files - it overrides both global and remote configs.</p>\n<p>For project-specific TUI settings, add <code>tui.json</code> alongside it.</p>\n<div class=\"aside\">\n<div class=\"aside-t\">Tip</div>\n<p>Place project specific config in the root of your project.</p>\n</div>\n<p>When OpenCode starts up, it first looks for a config file in the current directory, then traverses up to the nearest Git directory.</p>\n<p>This is also safe to be checked into Git and uses the same schema as the global one.</p>\n<hr />\n<h3 id=\"custom-path\">Custom path</h3>\n<p>Specify a custom config file path using the <code>OPENCODE_CONFIG</code> environment variable.</p>\n<pre><code class=\"language-bash\">export OPENCODE_CONFIG=/path/to/my/custom-config.json\nopencode run &quot;Hello world&quot;\n</code></pre>\n<p>Custom config is loaded between global and project configs in the precedence order.</p>\n<hr />\n<h3 id=\"custom-directory\">Custom directory</h3>\n<p>Specify a custom config directory using the <code>OPENCODE_CONFIG_DIR</code>\nenvironment variable. This directory will be searched for agents, commands,\nmodes, and plugins just like the standard <code>.opencode</code> directory, and should\nfollow the same structure.</p>\n<pre><code class=\"language-bash\">export OPENCODE_CONFIG_DIR=/path/to/my/config-directory\nopencode run &quot;Hello world&quot;\n</code></pre>\n<p>The custom directory is loaded after the global config and <code>.opencode</code> directories, so it <strong>can override</strong> their settings.</p>\n<hr />\n<h3 id=\"managed-settings\">Managed settings</h3>\n<p>Organizations can enforce configuration that users cannot override. Managed settings are loaded at the highest priority tier.</p>\n<h4 id=\"file-based\">File-based</h4>\n<p>Drop an <code>opencode.json</code> or <code>opencode.jsonc</code> file in the system managed config directory:</p>\n<table>\n<thead>\n<tr>\n<th>Platform</th>\n<th>Path</th>\n</tr>\n</thead>\n<tbody>\n<tr>\n<td>macOS</td>\n<td><code>/Library/Application Support/opencode/</code></td>\n</tr>\n<tr>\n<td>Linux</td>\n<td><code>/etc/opencode/</code></td>\n</tr>\n<tr>\n<td>Windows</td>\n<td><code>%ProgramData%\\opencode</code></td>\n</tr>\n</tbody>\n</table>\n<p>These directories require admin/root access to write, so users cannot modify them.</p>\n<h4 id=\"macos-managed-preferences\">macOS managed preferences</h4>\n<p>On macOS, OpenCode reads managed preferences from the <code>ai.opencode.managed</code> preference domain.
