## 1. Qué hay que hacer

`bun ./paquetes/rige/arranque/rige.ts servir` comprueba el estado del almacén con `consultarEstado` antes de escuchar. Si el almacén es compatible, escucha en `127.0.0.1:<RIGE_PUERTO>` y `GET /` presenta el mismo `RespuestaEstado` que devuelve la CLI. Si no, termina con `almacen-sin-esquema` (código 1) sin crear ni alterar nada. Si el puerto está ocupado, termina con `puerto-ocupado` (código 1). Se agrega además el cliente HTTP de pruebas de D-2.

**No** se hace en esta tarea (va en T0-12):
- la verificación de `Host`;
- la restricción a GET;
- el rechazo de `Sec-Fetch-Site`;
- la ausencia de CORS;
- la prueba exhaustiva del escape (`intermedios/origen.ts`, `RNF-09.test.ts`).

## 3. Interfaces

**Decisiones del ingeniero para esta tarea (no están en los ADR):**
- `servir`, ya escuchando, escribe en la salida una línea: `{"esquema":1,"direccion":"http://127.0.0.1:<puerto>"}`. El canal de error queda vacío y el proceso sigue vivo.
- `GET /` consulta el estado en cada solicitud: la web presenta lo que lee.
- El error de uso se responde con 503, la falla interna con 500 y la ruta inexistente con 404, siempre con página HTML fija.
- `argumentos-invalidos` e `interno` siguen fuera de `ErrorUso`: son códigos de la interfaz, no errores de uso de la aplicación.

**`arranque/rige.ts`:** `ensamblar` suma `consultarEstado: () => consultarEstado(almacen)` e `iniciarServidor: () => iniciarServidor(configuracion.puerto, () => consultarEstado(almacen))`. Lo demás no cambia: el arranque sigue sin capturar excepciones ni llamar casos de uso fuera de `ensamblar`.

## 4. Patrones existentes a imitar

- **CLI:** ampliá `interfaces/cli/ejecutar.ts` sin cambiar su forma:
  - un `try` solo para `parseArgs`, que da 2;
  - un único `try/catch` para el resto, que da 70;
  - `JSON.stringify(…) + "\n"`;
  - errores con `{ esquema: 1, error }`.

  `servir` sigue el mismo orden que `esquema`: ensamblado → `consultarEstado` → `iniciarServidor`. Cada `Resultado` fallido da 1.
- **Pruebas de la CLI:** imitá `ejecutar.test.ts`: el `ensamblar` es un doble, los canales acumulan texto y la función que no debe llamarse lanza `new Error("No debe …")`.
- **Imports de interfaces:** solo `aplicacion/casos-uso/*`, `aplicacion/respuestas/*`, `aplicacion/errores` y la propia capa `interfaces/`. Los tipos de los casos de uso se toman con `import type { … }` y `ReturnType<typeof …>`, como `CasosUsoCli` hace con `prepararAlmacen`. Nunca puertos, adaptadores ni núcleo.
- **Errores de uso:** imitá `errorConfiguracionInvalida` en `aplicacion/errores.ts`: función que devuelve `{ codigo, mensaje }` y mensaje sin tildes.
- **Subprocesos y temporales:** imitá `pruebas/aceptacion/arranque.test.ts`:
  - el helper `lanzar` obtiene el puerto libre con `Bun.listen({ hostname: "127.0.0.1", port: 0 })` y lo libera;
  - el entorno sale de `crearEntornoAislado`;
  - los temporales se registran y se borran en `afterEach`.

  Para `servir`, usá `Bun.spawn` (no `spawnSync`) y leé `stdout` hasta la primera línea. En `finally`, `proceso.kill()` y `await proceso.exited`. Nunca dejes un servidor vivo al terminar una prueba.
- **Guarda de red:** solo `pruebas/utilidades/cliente-http-local.ts` importa `node:http`. Su `.test.ts` importa el cliente, no `node:http`. `fetch` global sigue fallando en las pruebas (precarga): no lo uses.
- **Mensajes:** sin tildes en los mensajes de error, como `aplicacion/errores.ts`. Las páginas HTML sí pueden llevar tildes (UTF-8, `<html lang="es">`).

## 5. Reglas de comportamiento (una prueba por regla, con el ID en el `describe`)

| ID | Regla |
|---|---|
| W-1 | `html` escapa `&`, `<`, `>`, `"` y `'` en todo valor interpolado. `html\`<p>${"<script>alert(1)</script>"}</p>\`` no contiene `<script`. Un `HtmlSeguro` (de `sinEscapar` o de otro `html`) se inserta sin escapar |
| W-2 | `paginaInicio` responde 200, `text/html; charset=utf-8`, con «RIGE 0.1.0», la ruta del almacén y la versión de su esquema, tomadas de la respuesta. Una ruta con `<script>` aparece escapada, como texto. La página no tiene ningún `<script` |
| W-3 | `conErrores`: si el manejador lanza, la respuesta es 500 con la página fija, sin el mensaje ni el stack de la excepción. `paginaErrorUso(errorAlmacenSinEsquema)` da 503 con el mensaje escapado, que nombra `bun run esquema` |
| W-4 | `crearManejador`: `GET /` con estado exitoso → 200 de `paginaInicio`. Con `almacen-sin-esquema` → 503. `GET /otra` → 404 sin consultar el estado. Una excepción de `consultar` → 500 |
| W-5 | `iniciarServidor` sobre un puerto ocupado por un `Bun.listen` en `127.0.0.1` devuelve `puerto-ocupado`, cuyo mensaje nombra `RIGE_PUERTO`. Sobre un puerto libre devuelve `direccion = http://127.0.0.1:<puerto>` y `detener()` libera el puerto |
| H-1 | `solicitarLocal` con `host` distinto de `127.0.0.1` (`localhost`, `127.0.0.2`) rechaza sin conectar: un `Bun.listen` de control no recibe ninguna conexión |
| H-2 | `solicitarLocal` con `cabeceras: { Host: "ajeno.example" }` conecta a `127.0.0.1`. Un servidor local de prueba recibe la solicitud con ese `Host`, y el cliente devuelve estado, cabeceras y cuerpo |
| CLI-3 | (ampliada) Los errores de `parseArgs` dan `argumentos-invalidos` con mensaje propio en español, sin tildes, que nombra los argumentos recibidos (por ejemplo, `Argumentos invalidos: --x esquema.`); no se copia el texto de Node |
| CLI-6 | `servir` con dobles: `consultarEstado` fallido → 1 y `iniciarServidor` no se llama. `iniciarServidor` fallido → 1 con `puerto-ocupado`. Exitoso → salida `{"esquema":1,"direccion":"…"}` + `"\n"`, error vacío y código 0. Una excepción → 70. `esquema` no llama a `consultarEstado` ni a `iniciarServidor` |
| A-5 | Subproceso `servir`, con base preparada antes por `esquema` y puerto libre. La primera línea de stdout es la dirección y stderr queda vacío. `GET /` con `solicitarLocal` → 200 con «RIGE 0.1.0», la misma ruta y la misma versión que el JSON de `esquema` (paridad). `GET /otra` → 404 |
| A-6 | Subproceso `servir` con `RIGE_ALMACEN` en una carpeta inexistente: código 1, stdout vacío, stderr `almacen-sin-esquema` con `bun run esquema`. Después no existe la carpeta ni `rige.db`. Con una base de `user_version = 2`: código 1, y la base sigue en `user_version = 2` |
| A-7 | Subproceso `servir` con base preparada y `RIGE_PUERTO` ocupado por un `Bun.listen` de la prueba en `127.0.0.1`: código 1, stdout vacío, stderr `puerto-ocupado`, cuyo mensaje nombra `RIGE_PUERTO` |

## 6. Pruebas

- **Unitarias** (W, H, CLI), junto al código. W-1 a W-4 y CLI son puras: `Request` y `Response` en memoria, sin servidor. W-5, H-1 y H-2 abren sockets solo en `127.0.0.1`, con puerto libre obtenido en la prueba, y los cierran en `finally`.
- **Aceptación** (A), en `pruebas/aceptacion/arranque.test.ts`, por subproceso, según §4. Nunca se usa el puerto 4747, el almacén real ni `process.env` modificado.
- El rojo de cada regla se observa antes del código. Si el código ya la satisface, el rojo se observa con una mutación temporal revertida y así se registra.
